# 围绕一份制度的 AI 问询：设计方案

> 状态：**设计草案 v0.1（2026-11-24），待评审。**本文回答「选中一份制度问 AI」怎么做：交给 AI 什么、按什么顺序、谁来决定，以及技能（skill）元数据在其中的作用。
> 先写最佳方案（第 1–6 节），再写今天的差距和实施顺序（第 7–9 节）。凡标「提案」的数据模型改动，按 [AGENTS.md](../AGENTS.md) 须经设计评审后再建。
> 依据：11-24 会议意见（[`review-2026-11-24.md`](review-2026-11-24.md)，下文 M1–M12 指其中编号）；实测记录（[`evaluation-2026-11-23.md`](evaluation-2026-11-23.md)）；ObjectStack 平台代码核对；主流平台调研（第 10 节）。

## 0 结论

| 问题 | 结论 |
|---|---|
| 能不能选中一份制度直接问 | 能，而且应当是主要问法之一（M5 ②）。范围是对话的显式状态，钉在对话上 |
| 制度要不要拆条款，还是整份交给 AI | **问一份指定的制度时，整份交给 AI。**实测整份全文喂给模型 26/26 正确、每题约 2,000 输入 token、中位 3.3 秒，优于所有按条检索的做法（第 2.1 节）。条款不再是维护单位，而是由全文自动拆出的派生索引，用于引用链接、通用问的定位、版本对比 |
| 字段全传还是挑着传 | 挑着传。字段分三档：必送 / 按需 / 不出域，写在对象元数据里，由平台执行 |
| 相关制度怎么用 | 用有类型的制度关系（依据、引用、配套、替代 / 废止、冲突）。默认只告诉 AI 关系和名称，被引用或本制度未规定时才读对方，答复分开标注来源 |
| 子表、关联表、附件怎么用 | 子表（版本、条款）：读定稿版本全文；关联表：导航，按需展开；附件分三类：规范性附件当正文、表单交给用户、原件不发给模型 |
| 技能起什么作用 | 技能写「做事方法」（怎么读、怎么引用、何时转人工），按场景拆成几个，按上下文启用，并指定用哪套「情境包」。数据范围、权限、出域不靠技能保证 |

## 1 目标设计总览

### 1.1 一句话

**元数据声明「能给 AI 什么、默认给什么」；服务端以提问人的身份把确定的部分直接放进提示词；AI 只决定「这个问题还要再读什么」。**

今天的做法把这三件事全交给模型：只告诉它一个记录 id，读哪些字段、读不读条款、读不读关联制度都由它临场决定。实测 MCP 目录路线每题 4–6 万输入 token、约 10 秒，主要花在一轮轮试探上。

### 1.2 流程

```
用户在制度详情页点「问这份制度」（或在 AI 面板选择范围）
          │
          ▼
输入框上方出现范围标签：「制度 · 差旅费报销管理办法 · V3.0」（可移除、可追加一份做对比）
          │
          ▼
服务端以提问人身份读取，按固定顺序拼进提示词：
  智能体说明 → 启用的技能说明 → 工具 → 当前应用
  → L0 制度卡片（必送字段）
  → L1 目录（关联制度：关系 + 名称 + 状态；附件清单）
  → L2 定稿版本全文（正文 + 规范性附件）           ← 制度不长时整份放入
          │
          ▼
模型作答；只有需要时才调用工具：读关联制度的命中条款、取表单文件、转人工
          │
          ▼
答复：结论先行 + 出处（制度、版本、第 X 条，可点开）+ 「依据」区列出用到的制度和版本（M5）
```

### 1.3 范围（scope）

- 范围 = 一个或多个记录引用 `{ object, id }`。制度问询有三种：不限（通用问）、一份制度（读它的定稿版本）、一个版本（M5）。
- **范围钉在对话上**，不随浏览器地址变化。用户边问边去翻另一份制度时，范围不悄悄更换；要换，界面询问「改为问《X》？」。理由：答复必须说明依据（M5），范围漂移会让同一对话前后依据不一致。
- 范围是提示，不是授权：选中一条自己读不到的记录，结果是「找不到」。
- 选中一份制度后问题超出它：先说「本制度未规定」，再给出全库查询的结果并标明来源；不悄悄扩大范围。

### 1.4 记录情境包（record context pack）

| 层 | 内容 | 谁决定 | 怎样到达模型 |
|---|---|---|---|
| L0 卡片 | 制度自身的「必送」字段，带标签，一行一项 | 对象元数据 | 服务端读取后写进提示词 |
| L1 目录 | 关联制度（关系类型、名称、状态）、附件清单（名称、类别、有无文本）；制度很长时还有条款大纲 | 对象元数据 | 同上 |
| L2 正文 | 定稿版本全文：不超过阈值时整份放入；超过时放大纲 + 本制度内检索的命中部分 | 元数据给阈值，服务端按版本的 `text_tokens` 判定 | 同上；关联制度的正文由模型按需取 |

L0、L1 和不超阈值的 L2 由服务端注入，而不是让模型调用工具：结果确定（不会漏读），省掉往返，权限和出域规则在一处执行、不依赖模型听话。顺序固定、前缀不变，可以走提示词缓存（实测 2,000 token 的输入里约 1,800 命中缓存）。

## 2 制度场景的情境模型

### 2.1 正文：整份优先，条款是派生索引

**实测（`deepseek-flash`，一份脱敏的真实集团接待管理制度，正文约 3,100 字、25 条、8 章）：**

| 做法 | 结果 | 每题耗时中位 | 每题输入 token |
|---|---|---|---|
| 整份全文放进提示词，不给工具 | 26/26 正确（12 道有依据 + 1 道无依据，各 2 次） | 3.3 秒 | 约 2,000（约 1,800 命中缓存） |
| 拆条检索前 8 条 + 模型判断（表单问询现状） | 12/12 符合预期 | 多数 2–7 秒 | — |
| MCP 目录路线（模型逐步查目录、读条款） | 12/12 | 约 10 秒 | 4–6 万 |
| 拆条检索、直接摘录第一名（旧做法） | 8/12 正确作答，3/12 答错 | < 1 秒 | — |

结论：

1. **问一份指定制度时，整份放入。**制度问询的错误多数来自漏读（例外、定义、附则、「按第 X 条执行」）。整份放入从根上消除这一类错误，而且最快最省。
2. **阈值**：版本导入时计算 `text_tokens`，不超过阈值（建议起点 12,000 token，约 1.5–2 万字，可覆盖绝大多数制度）整份放入；超过时放条款大纲 + 本制度内检索的命中部分，并固定带上总则、附则和被命中条款引用的条款。阈值用题集实测后再定。
3. **条款的角色改变**（与 M6 一致）：条款不人工维护，由版本全文自动拆出，版本一改全部重新生成。它用于：
   - 答复里的出处精确到「第 X 条」并可点开；
   - 不指定制度的通用问：先定位到制度（见 2.2）；
   - 版本对比、发布前一致性检查：按条对齐；
   - 超阈值的长制度：在本制度内检索。
4. 同一对话里全文只放入一次；第二个问题直接沿用。

### 2.2 不指定制度的通用问

1. 模型先读**制度目录**（每份制度一行：名称、分类、摘要、现行版本、生效状态）。制度少时目录本身很短。
2. 选出 1–3 份相关制度，**读这几份的全文**（各自按 2.1 的阈值）。
3. 制度多到目录摘要分辨不清时，再用按条检索（向量或关键词）辅助定位制度，命中条款只用来找到制度，作答仍读全文。
4. 答复列出用到的全部制度和版本。

### 2.3 自身字段：怎么选

选择原则：**这个字段会不会改变答案或答案的可信度。**

| 组 | 字段 | 档 | 理由 |
|---|---|---|---|
| 身份与引用 | 制度名称、制度编号、发文文号、现行版本号 | 必送 | 每条答复都要引用 |
| 效力 | 状态、生效日期、（废止日期、被哪份制度替代） | 必送 | 决定能不能当依据；已废止的要先说明 |
| 适用与责任 | 制度层级、发文单位、归口部门、协同部门、适用范围 | 必送 | 「找谁」「适用于我吗」是高频问题；转人工要写归口部门 |
| 导航 | 目录摘要、分类、关键词 | 必送（摘要）/ 按需 | 判断问题是否在本制度范围内 |
| 管理过程 | 下次复审日、负责人、审议 / 决议主体、修改记录 | 按需 | 员工问询用不到；维护、审计场景由各自的情境包列入卡片 |
| 内部与敏感 | 诊断意见、讨论、脱敏对照、原文 | 不出域或仅管理员 | M4、M8 |

三条规则：

1. **卡片是白名单**：没列的字段不进卡片。新增字段默认「按需」，不会因为加字段就悄悄变贵或泄露。
2. **「不出域」由平台在所有 AI 读取出口执行**（应用内对话的数据工具、MCP、知识索引、情境包渲染）。它和字段级安全是两件事：字段级安全回答「这个人能不能看」，出域回答「这段内容能不能发给外部模型」。M8 要求「展示原文、发给 AI 的只能是脱敏文」，正是后者。
3. 被字段级安全遮住的字段，卡片上写「对你不可见」，不写成空。

### 2.4 子表：版本

- 范围是制度时只读**定稿（现行）版本**（M5）；范围是版本时读该版本。
- 历史版本只在对比、审计场景读，且只给制度管理员；员工问询只问定稿版本。
- 卡片里只放现行版本号；版本列表不进员工问询的目录。

### 2.5 关联记录：关系有类型，标题进目录，正文按需

- 关系类型至少：依据（上位）、引用（正文里点名）、配套（实施细则、表单）、替代 / 废止、冲突（经人工确认）。
- L1 目录里列关系类型、对方名称、对方状态，例如「引用 · 《费用报销管理规定》· 已发布」「废止 · 6 份旧文件」。
- 模型**何时去读对方**：
  - 被引条款把事情交给了对方（「按《费用报销管理规定》执行」）→ 读对方全文中相关部分（对方也短时同样整份读）；
  - 本制度确实没有规定 → 先说明，再查并标注来源；
  - 问「这份还有效吗 / 被什么替代了」→ 只用关系和状态回答。
- 被替代 / 废止的制度**永远不作依据**，只用于说明沿革。
- 答复分开写：「依据本制度：……」「依据关联制度《X》V__：……」。
- 关系的来源：导入时自动抽取正文里的书名号引用和废止清单，生成**待确认**关系，由制度管理员确认；未确认的只作导航提示，不作依据。

### 2.6 附件：三类，三种用法

| 类别 | 例子 | 存储 | AI 怎么用 |
|---|---|---|---|
| 规范性附件（制度内容的一部分） | 标准表、分级明细、填写要求 | 转 Markdown，并入版本全文，出处写「附件 1」 | 与正文一样：计入全文，可引用 |
| 表单模板（要用户去填） | 审批表、清单 | 原件放文件字段；另存一段文字说明（有哪些栏、谁签字） | 读说明，不读原件；答复里**把文件交给用户**（下载链接或「发起」动作） |
| 原件与证据 | 红头签章件、扫描件 | 文件字段 | 不发给模型；界面上供人核对 |

图片型附件先文字化；无法文字化的在目录里标「无文本」，模型据此请用户查看原件，不编内容。

### 2.7 token 预算

| 项 | 办法 |
|---|---|
| 减少调用次数 | L0、L1、全文由服务端放入，目标是一次模型调用作答；今天 MCP 目录路线是 4–6 次 |
| 固定前缀走缓存 | 说明、技能、工具放最前且不变 |
| 只给需要的工具 | 范围内问询只需读关联制度、取文件、转人工几个工具，不需要 17 个 |
| 全文阈值 | 按 `text_tokens` 判定整份 / 检索，不靠模型估 |
| 关联制度 | 只读需要的那份，且仍受阈值约束 |
| 对话内不重读 | 全文留在历史里；长对话压缩时保留卡片、目录和已引用的部分 |
| 分模型 | 日常问询用便宜模型；诊断、一致性检查用强模型，后台跑 |

### 2.8 权限与出域

- 卡片、目录、全文一律以**提问人**身份读取：对象权限、行级共享、字段级安全全部生效。读不到的关联制度不出现在目录里。
- 草稿版本、诊断意见只对制度管理员可读。诊断不能挂成版本的主从子表，否则权限跟随版本（见 review 第 3 节）。
- 出域：发给模型的每段文本先过出域过滤；答复展示前用对照表还原（M8）。对照表本身不出域、仅管理员可读。

## 3 技能（skill）元数据：怎么用

### 3.1 技能能声明什么（平台现状，已核对）

| 键 | 含义 | 应用内对话 | MCP |
|---|---|---|---|
| `name` / `label` / `description` | 标识和说明 | 写进系统提示词的「Active Skills」段 | 作为提示词名称和描述（本应用为 `brightrule-brightrule_policy_inquiry`） |
| `surface` | 属于哪个内置智能体（`ask` / `build` / `both`） | 与智能体不匹配时报错 | 不读 |
| `instructions` | 做事方法 | 启用时全文拼进提示词，每轮都带 | 投影为 MCP 提示词 |
| `tools` | 绑定的工具，支持 `action_*` 通配 | 智能体工具集 = 各启用技能工具的并集 | 只决定是否下发：这条连接提供了全部绑定工具，技能才出现在提示词列表 |
| `triggerConditions` | 按上下文启用（字段 / 运算符 / 值，全部满足才启用） | 可用字段有 `appName`、`objectName`、`recordId`、`userRole` 等 | 不读 |
| `active` / `mcpPrompt` | 开关；`mcpPrompt: false` 表示不在 MCP 下发 | — | — |
| `permissions` | **不存在**，写了会被拒绝 | 权限在智能体和工具上 | 同左 |

依据：`objectstack/packages/spec/src/ai/skill.zod.ts`（规范）、`objectstack/packages/mcp/src/skill-prompts.ts`（MCP 下发）；应用内对话的行为见 objectstack-ai/cloud#4935。

### 3.2 技能带来什么（实测）

同一模型、同一批工具，有没有技能说明的差别（评测第 3、4 节）：引用条款 4/9 → 27/27；结尾声明 0 → 全部；无依据转人工 0 → 全部；MCP 每题输入 token 约 9.8 万 → 约 4.8 万。

**技能负责做事方法**：读什么、按什么顺序、怎么引用、何时说「没有规定」、何时转人工、不许自己造记录。**技能不负责**：权限（没有门，也不该有）、数据范围（「只读定稿版本」写在说明里模型可能不照做，应由情境包保证）、出域（平台的事）。

### 3.3 按场景拆成 5 个技能（目标）

| 技能 | 启用条件 | 说明要点 | 情境包 | MCP |
|---|---|---|---|---|
| `brightrule_inquiry_general` 通用问询 | 明规应用内，没有选中制度 / 版本 | 第 2.2 节：目录 → 选 1–3 份 → 读全文；跨制度比对规则 | 制度目录 | 下发 |
| `brightrule_inquiry_scoped` 选中制度 / 版本问询 | 上下文里有制度或版本记录 | 卡片、目录、全文已在上下文里，不要再查；离开本制度要说明；关联制度按 2.5 读；答复列依据 | `inquiry` | 下发；说明里写明「通过 MCP 时用户会点名制度，先按名称找到它」 |
| `brightrule_cross_policy` 跨制度分析 | 问「互斥 / 冲突 / 重叠」类问题 | 定口径、定范围、只认真矛盾、发现即转人工（现有技能的规则） | 制度目录 | 下发；暂并入通用问询（平台没有按问题内容启用技能的机制） |
| `brightrule_maintain` 制度办维护 | 上下文里有版本记录，用户是制度管理员 | 版本对比由动作算好差异、模型只解释；诊断、一致性检查调用动作后台执行 | `maintain` | 不下发 |
| `brightrule_answer_desk` 人工答复 | 上下文里有问询记录，用户是制度管理员 | 读问题、AI 部分答复和依据，起草答复，写回前由人确认 | `inquiry` | 不下发 |

### 3.4 技能与情境包的分工

1. 对象声明**有哪些情境包**（`inquiry`、`maintain`、`review`）和字段出域级别——数据的属性。
2. 技能声明**启用时用哪一份**——场景的属性。
3. 一轮对话：范围记录 → 触发条件选出技能 → 技能指定情境包 → 服务端以提问人身份渲染 → 技能说明讲怎么用。

「能给什么、哪些不出域」放对象（合规属性），「这个场景用哪一份」放技能。两处都放会漂移。

## 4 场景矩阵

「读什么」四列：自身字段 / 子表 / 关联 / 附件。

| # | 场景 | 入口 | 自身字段 | 子表 | 关联 | 附件 | 输出 |
|---|---|---|---|---|---|---|---|
| A | 员工问选中的制度（M5 ②） | 制度详情「问这份制度」 | 问询卡片 | 定稿版本全文 | 目录列关系；被引或未规定时读对方 | 规范性附件并入全文；表单给文件 | 结论 + 出处 + 依据区 |
| B | 员工问选中的版本（M5 ③） | 版本详情「问这个版本」 | 版本卡片 + 制度卡片 | 该版本全文 | 同 A | 该版本附件 | 同 A，非现行版本先说明 |
| C | 员工通用问（M5 ①） | 首页问询框；AI 面板无范围 | 制度目录 | 选中 1–3 份的全文 | 命中制度的关系 | 同 A | 同 A，列出全部依据 |

## 5 入口与界面

1. 制度详情页、版本详情页：主按钮「问这份制度」「问这个版本」，打开 AI 面板并带上范围标签，附 3 个起手问题（由摘要生成或人工配置）。
2. 制度库列表：行内「问」图标；多选后「问所选制度」（对比、汇总）。
3. AI 面板：范围标签可移除、可追加；无范围即通用问。
4. 记录以抽屉 / 弹窗打开时，AI 面板必须仍然可达（并排，或抽屉标题栏里有同一入口）。
5. 答复里的出处是链接，点开到对应条款或全文位置；「依据」区列出用到的制度和版本（M5）。
6. 表单问询（「我要问询」）保留：它留痕、可转人工、可评测。

## 10 与主流平台的对比

### 10.1 各平台做法（调研摘要）

| 平台 | 选中记录怎样到达 AI | 字段选择 | 子记录、关联、附件 |
|---|---|---|---|
| Twenty CRM（读了源码） | 只发指针（对象名 + 记录 id），服务端附在用户消息里 | 模型调用查询工具时必须指定字段；工具按角色剔除不可读字段 | 按需查询，默认 10 条、最多 100 条；会话过长时剪枝历史 |
| Salesforce Agentforce / Prompt Builder | 开放对话：记录 id + 动作拉取；固定用例：模板 + 合并字段推送 | 模板里显式引用；关联列表字段按用户的页面布局 | 附件走检索，可按记录 id 预过滤；信任层做脱敏和审计 |
| Microsoft Dynamics 365 | 记录摘要等固定用例 | 管理员选字段（销售摘要 4–15 个，可跨关联表） | 关联表按配置带入 |
| ServiceNow Now Assist | 按记录状态切换不同输入模板 | 管理员声明，字段须写描述 | 按模板配置 |
| HubSpot / Notion / Airtable / Attio | 固定字段集，或用户 @ 点名 | 显式引用 | 沿用用户本人权限 |

共同规律：没有平台默认把全部字段发给模型；固定用例用「模板 + 推送」，开放对话用「指针 + 工具拉取」；附件走检索；AI 不另设权限，一律以用户身份取数；调研范围内没有见到按字段设置「对 AI 不可见」的官方做法。

### 10.2 本设计采纳的

- 开放追问用「指针 + 按需拉取」（关联制度、表单文件）；
- 确定的部分用「声明字段子集 + 主动推送」（卡片、目录），卡片是白名单；
- 一个场景一份配方，由条件决定用哪份（ServiceNow 的状态模板、Salesforce 的用例模板）；
- 用户显式指定范围（Dynamics、Attio、Notion 的 @ / 选择器）；记录页一键入口（Salesforce 记录页快捷动作）；
- 以用户身份取数，不另设 AI 权限。

### 10.3 有意不同的

| 本设计 | 多数平台 | 理由 |
|---|---|---|
| 子表正文（制度全文）整份放入 | 长文本分块检索，子记录默认取很少 | CRM 子记录彼此独立；制度条款是一份文档的各部分，例外、定义、附则会改变答案。实测整份放入 26/26，检索第一名 12 题错 3 题 |
| 范围钉在对话上 | 上下文跟随当前页面 | 答复必须说明依据，范围漂移会使依据前后不一致 |
| 字段级「不出域」，平台强制 | 无现成做法 | M8：同一条记录原文给人看、脱敏文给模型，字段级安全表达不了「人能看、模型不能看」 |
| 关系有类型，按类型决定是否跟过去 | 关联记录同质 | 被替代的不能当依据，被引用的才需要读 |
| 附件分三类，表单交给用户 | 附件统一进检索索引 | 员工问「用哪张表」要的是文件本身 |

## 11 待决事项

| # | 事项 | 建议 |
|---|---|---|
| 1 | 原文会不会被发给外部模型。今天只要用户能读的字段，应用内对话和 MCP 就能读到 | 在 N3 落地前，原文不放进 AI 能读到的文本字段。这是 M8 的底线，优先于体验 |
