# 制度文件导入方案（B2：脱敏、打包、写入）

> **2026-11-25 更新**：「版本文档」已改为「正文写在版本上 + 附件子表」，导入写入的对象随之变化，见 [`policy-version-body.md`](policy-version-body.md)。下文中的「版本文档」按此理解。
> 状态：**已实现第一版**（`tools/redact/package.py`、`importer.py`，用法见 `tools/redact/README.md`），口径已按 PR #25 的 `docs/policy-document.md` 对齐：不存原文偏移、内容哈希只算原件文件、token = 字数 ÷ 1.5。下文的设计细节以代码和 README 为准。
> 原状态：方案，待评审。 依据《制度问询与知识检索：详细设计 v0.2》（2026-11-24）的已定事项、第 2.1 节「版本文档」、第五节 B2 和 D6、D8、D9。
> 本文只讲「本地的 Word 原件怎么变成系统里的制度、版本和版本文档」。数据模型本身（B1）另行评审，导入排在它后面。

## 1 结论

**在 Mac 本地跑完四步，系统里就有了可问询的制度**：转换 → 扫描并确认词典 → 脱敏 → 打包、核对批次清单 → 导入。
前三步的工具已经有了（`tools/redact`），要新增的是**打包**和**导入**两个命令。

| 进系统的 | 留在本地的 |
|---|---|
| 原件文件（正文、每个附件各一份 docx），员工预览、下载看原文 | 词典、对照表、替换汇总（含原文） |
| 脱敏 Markdown（正文、每个附件），模型和检索只读它 | 原件 Markdown（只用来算条号索引里的原文位置） |
| 条号索引、字数、token 估算、内容哈希 | 转换报告、脱敏报告 |
| 制度和版本的元数据（名称、编号、文号、日期……），**是原文**，见第 9 节第 1 项 | |

## 2 全流程

```
原件/（.doc .docx，可有子目录）
  │ ① ./run.sh convert --input 原件                 .doc → 同名 .docx（已有）
  │ ② ./run.sh scan --input 原件  → 人工确认词典      （已有）
  │ ③ ./run.sh --input 原件 --dict 词典.csv          脱敏（已有）
  ▼
脱敏结果/<批次>/
  │ ④ ./run.sh package --run 脱敏结果/<批次>          新增：生成导入包 + 批次清单（预填）+ 检查报告
  │    人工核对「批次清单.csv」和「检查报告.md」
  ▼
导入包/<批次>/
  │ ⑤ ./run.sh import --package 导入包/<批次> --url https://… [--apply]
  │    默认只预演（列出要新建、更新、跳过、拒绝的记录）；加 --apply 才写入
  ▼
系统：制度 → 版本（草稿）→ 版本文档（原件文件 + 脱敏正文）→ 制度关系（待确认）
  │ ⑥ 管理员在系统里核对后把版本设为现行（设计场景 E 第 4 步）
```

导入只建**草稿**版本，不自动设为现行，员工在设为现行之前看不到。

## 3 导入包（第 ④ 步的产物）

一个版本一个文件夹，原件和脱敏件按同一结构存放：

```
导入包/20261125-15/
├── 批次清单.csv                      ← 人工核对，导入以它为准
├── 检查报告.md                        ← 条号缺漏、附件分类、元数据缺项、关系待确认
└── 行政类/青松集团接待管理规定/
    ├── manifest.json                  ← 下文的字段
    ├── 正文.original.docx             ← 原件（进系统的文件字段）
    ├── 正文.redacted.md               ← 脱敏正文（进系统的文本字段）
    ├── 附件1-接待审批表.original.docx
    ├── 附件1-接待审批表.redacted.md
    └── …
```

> 导入包含原件，和「内部留存-勿外发」同级保管，不外发、不进 Git（`.gitignore` 已覆盖 `*.docx`，再加 `导入包/`）。

`manifest.json`（每个版本一份；字段对应设计 2.1 节的 `brightrule_policy_document`）：

## 4 批次清单（人工核对的唯一入口）

设计 B2b 要求的「制度编号、版本号、生效日期、分类、层级」放在一张表里，**一行一个版本**。打包时尽量预填，人工核对后导入只认这张表：

| 列 | 预填来源 | 必填 |
|---|---|---|
| 来源文件 | 原件相对路径 | 是 |
| 制度编号 | 正文开头「制度信息表」的「制度编码」 | 否；原文没有就留空，导入时按制度名称对应 |
| 制度名称 | 信息表「制度名称」；没有就取正文标题 | 是 |
| 版本号 | 发文文号（如 `HDB字〔2025〕2号`）；没有文号就填 `V1.0` | 是 |
| 生效日期 | 信息表「生效日期」；或正文「自××起施行」 | 否；原文没有就留空 |
| 发文日期 | 落款日期 | 否 |
| 分类、层级、归口部门、协同部门、审议主体、决议主体、关联制度 | 信息表对应格 | 否 |
| 状态 | 固定为「草稿」 | — |
| 导入 | 是 / 否（填「否」的行跳过） | — |

检查报告里把每份文件取不到的字段列出来，人工补到清单里。

## 5 条号索引（替代条款表，D6）

- **怎么切**：在脱敏 Markdown 里按「第X条」（含「第X条之一」）定位每一条，起点是条号，终点是下一条的条号或下一章的标题；附则、附件目录之后的文字不归入任何一条。章取前面最近的「第X章」。
- **两边对齐**：同样的规则在原件 Markdown 上再跑一遍，得到 `original` 区间；两边条数、条号序列必须完全一致，否则这份文件**拒绝打包**，在报告里写明差异（通常是词典替换改动了条号附近的文字）。原件 Markdown 只在本地用，不进系统。
- **进报告、等人工确认**（不拒绝）：条号不连续（如缺第五、六条）、重复、「之一」、条号是 Word 自动编号算出来的。
- 字数和 token：`text_chars` 按脱敏文计；`text_tokens` 按设计 P3.3 的统一公式（汉字每个计 1.5，其余每 4 个字符计 1，再加 10%）。

## 6 附件

- 拆分沿用现有规则（单独一行「附件N」到下一个附件或版记），**原件和脱敏件各拆一份**：原件附件 docx 进文件字段，脱敏附件 md 进文本字段。当前工具只拆了脱敏件，要补上原件。
- 默认分类（设计 2.1 节的 `attachment_class`），报告里列出，人工可在清单里改：
  - 表格里空格子超过一半 → **表单**（交给用户填）；
  - 其他 → **规范性**（并入全文给模型）；
  - **原件**（不发模型）只能人工指定。
- `index_title` 用脱敏后的标题，如「甲集团接待管理规定 · 附件 1」。

## 7 制度关系（B2c，导入后都是「待确认」）

- 正文里的《…》：规范化（去书名号、去「关于印发…的通知」外壳、全半角统一）后，与本批次和系统里已有制度的名称**精确匹配**才建链接，匹配不上只记 `to_title`。
- 「……表 / 单 / 清单」不建关系（多半是附件）；不能指向自己。
- 第一条「根据《…》制定」→ **依据**；「原《…》同时废止」→ **替代**；其余 → **引用**。
- 员工看不到待确认的关系，也不作为依据（设计 B1.3）。

## 8 写入规则（第 ⑤ 步）

- **顺序**：制度（按制度编号新建或更新）→ 版本（按制度 + 版本号）→ 版本文档（按版本 + 序号）→ 关系。
- **原件上传**：走平台的文件存储接口（`/api/v1/storage/upload/presigned` → 上传 → `/complete`），拿到文件 id 后写进 `original_file`。接口细节在实现时按当时的平台版本核对。
- **幂等**：版本文档按 `content_hash`（原件文件哈希 + 脱敏正文哈希）比对，一样就跳过；同一批次导两次，行数和哈希都不变。
- **不改现行版本**：目标版本已经是现行、内容又变了，**拒绝**，提示改版本号作为新版本导入。
- **预演**：默认只打印计划（新建 / 更新 / 跳过 / 拒绝，各多少条、为什么），加 `--apply` 才写入；写入后生成导入记录。
- **凭证**：系统地址用 `--url`；用 `--login` 运行时输入账号密码（平台的文件上传只认登录会话，API Key 传不了文件），凭证不写进任何文件、不打印。
- **身份**：用制度管理员的 Key 导入；导入不改权限，员工能看到什么仍由权限集决定（B1.5）。

## 9 需要确认的事

1. **制度元数据是原文**：制度名称、文号、发文单位会进系统并发给模型（例如「青松集团接待管理规定」）。设计第八节已把它列为接受的风险、脱敏增强延后。**客户名称会因此出现在发给模型的内容里**，请再确认一次可以接受；不接受的话，导入时把这几个字段也按词典替换，页面上显示脱敏名称。
2. **原件是 .doc 时上传哪份**：建议上传转换后的 .docx（系统能预览）；.doc 原件留在本地。
3. **版本号**：建议用发文文号；没有文号的用 `V1.0` 起排。
4. **一份 Word 里有多份制度**（合订本）：一期不拆，报告提示，人工先拆成多个文件。

## 10 任务与顺序

| 任务 | 内容 | 依赖 | 规模 |
|---|---|---|---|
| T1 原件附件拆分 | 脱敏时同时拆出原件附件 docx（放内部留存） | 无 | S |
| T2 元数据抽取 | 「制度信息表」、文号、落款日期、「自××起施行」→ 预填批次清单 | 无 | S–M |
| T3 条号索引与检查 | 第 5 节；原件 / 脱敏两边对齐；检查报告 | 无 | M |
| T4 附件分类与关系抽取 | 第 6、7 节 | T3 | S–M |
| T5 `./run.sh package` | 组装导入包、manifest、批次清单、检查报告；合成 Word 端到端测试 | T1–T4 | S |
| T6 `./run.sh import` | 第 8 节；预演、幂等、拒绝规则；对着本地 `os dev` 跑通 | **B1 数据模型合并**、T5 | M |

T1–T5 不依赖数据模型，可以马上做，产物先给业务方核对；T6 等 B1 评审通过后接上。全部只用合成数据做测试，真实制度不进仓库。

**验收**：用 5 份以上真实制度（本地）走完 ①–⑥：每份的条号索引点开都落在正确的那一条；附件可下载；重复导入不新增记录；预演和实际写入的计划一致；员工身份在设为现行前看不到、之后能问到。
