# 制度问询优化评估（2026-11-27）

> 状态：**评估结论，已经评审。** 维护者 2026-11-28 定：评测集做、放本仓库（#69）；第 3 节第 3、4 项立卡（#70、#71），均为 p1。

依据：brightrule `c51dd14`、cloud `7ac51e7`、objectstack `4b2855f7` 的代码和文档；brightrule 评测记录（2026-11-23/24）；2026-11-26 线上 130 题 × 千问 / DeepSeek 盲评的汇总（cloud#5099、cloud#5102、#66 里的数字，原始题目不在任何仓库）。本文只评估，不改代码。真实语料和真实题目不进本仓库，这里只写统计结论。

## 结论先行

1. **指定制度问（「问这份制度」）已经是强项**：资料包整份注入，真实接待制度 26/26 正确、中位 3.3 秒、约 2,000 输入 token。不需要向量。
2. **不指定制度的通用问是短板，规模一大就失效**：真实语料约 1,750–1,928 份，目录每行约 200–300 token，按技能规定的每页 50 条要 35–40 页、目录本身约 40–50 万 token，每轮还要重发历史（估算）。实际退化成模型自己拼 `$contains` 子串搜索：没有排序，口语说法搜不到（打车 vs 网约车），两字词又命中太多。线上 130 题里有 789 次在正文上做子串搜索，就是这个症状。**向量 / 混合检索要补的正是「定位」这一段**，作答仍然读整份。
3. **最大的失分不在检索，在「用错单位」和「无依据时编」**：下属公司 18 题两个模型都只对 3 题；无依据 15 题千问对 5、DeepSeek 对 3，各编造 2。平台已注入提问人和单位链（cloud#5099 已合），技能已改为本公司优先、无依据收口（#65 已合），但**两项都还没重跑验证**。
4. **权限现在全靠技能自觉**：brightrule 还没有任何行级规则，员工能读到全部制度，包括草稿、已废止和平级公司的（`inquirer.permission.ts` 注释、`policy.object.ts` 为 `public_read`）。约 93% 的制度是下属公司发的，不先隔离就上向量，前几名会被平级公司的同名制度占满，「用错单位」反而更重。**所以权限隔离要排在向量前面。**
5. **排序建议**：找回 130 题重跑 / 建评测集 → 已发布行级规则 + 目录按单位预筛（都是小改）→ 按单位隔离可见性 → 平台 cloud#5102 落地 → 引文逐字校验 → 平台向量就绪后上「检索定位、整份阅读」。重排、同义词表、GraphRAG 放后面或不做。
6. **没有现成的向量检索评测集**。第 4 节给出设计；推荐题集源头放 brightrule（公开仓库，只放合成语料），真实脱敏题集放仓库外，cloud 评测台钉版本引用同一份题集。

## 1 当前链路

| 环节 | 现在怎么做 | 问题 |
|---|---|---|
| 切段 | 不切。正文整份在 `brightrule_policy.body_md`，条文以加粗 `**第X条**` 开头（不是标题），附件各成一条 `brightrule_policy_attachment`。旧条款表和自写 pgvector 已在 #19 / `68f6238` 删除 | 平台的 markdown 切分会自动带标题路径一起向量化，但加粗条号不是标题，要在导入时转成标题 |
| 定位：指定制度 | 「问这份制度」钉住记录，资料包 `brightrule_policy_reading` 把目录字段、正文、附件（≤20）以提问人身份注入 | 无长度阈值（设计稿建议 12,000 token 起，未实现） |
| 定位：通用问 | `query_records` 读目录（技能要求每次带 `status = published`、每页 50、不取正文），可在 title / summary / body_md 上 `$contains`，模型挑 1–3 份 | 见结论 2。每页 50 是技能自定的，平台上限 200；summary 常为空，目录辨识度低 |
| 阅读 | `get_record` 整份正文 + 附件；附件按 label 对照；`has_images` 时说明需看原件 | 正确，是现有路线的核心优势（不漏例外、附则） |
| 权限 | 全部以提问人身份读，但**还没有行级规则**：员工读得到全部制度（草稿、已废止、平级公司）。「只答已发布」「不用平级公司」都靠技能 | 见结论 4。平台知识检索是先召回、再按权限过滤、只补一轮，隔离后检索还需按单位前置过滤 |
| 单位与反问 | 平台在每会话半段注入提问人、所属公司、单位链（cloud#5099 / PR #5107，只对登录会话，MCP 没有）。技能：本公司优先 → 集团（注明）→ 平级不作答；规定不同且不知单位时才问一次；职级分档全列 | 部署后未重跑 |
| 回答格式 | 固定「结论 / 依据 / 出处」三段，出处写 [显示名](链接) 文号 第X条，末尾声明 | 链接只到制度，不到条；依据里的引文不校验是否逐字存在 |
| 无依据 | 换 2–3 组关键词仍没有就答未找到，不按别家给做法，不编部门（#65） | 未重跑 |
| 跨制度冲突 | 问时临时读相关制度全文比对 | 小语料可行；规模大应改为发布时检查（「AI 诊断」按钮还是占位） |
| 平台开销 | 351/356 个对话第一步查应用文档；文档和结构探查占 42.6% 工具调用、每对话约 2.9 轮 / 3.4 万 token（cloud#5102，p1，未落地）。技能文本约 4,500 / 5,600 字符预算 | 新规则只剩约 1,000 字符可写 |
| 知识检索前提 | service-knowledge 的同步已按知识源 `where` 过滤（事件和重建路径都重读行），产品简报 §7.3 提的前置问题已修 | 知识源需声明 `where: status = published` |

## 4 评测集设计

### 4.1 现状

| 已有 | 内容 | 局限 |
|---|---|---|
| brightrule `scripts/eval/questions.json` + `mcp-eval.mjs` | 13 题，合成种子，关键词判分，走 MCP + 客户自带模型 | 条款时代写的，规模小；MCP 没有提问人块；不测检索 |
| `docs/evaluation-2026-11-23.md` 第 7 节 | 真实接待制度 12 题 | 只在本地，单份制度 |
| 2026-11-26 线上 130 题 × 2 模型，Fable 盲评 | 端到端 2/1/0 分，满分 258 | 题目和结果不在仓库；没有检索层；没有权限题 |
| #8（未做） | 目录定位在 100 / 300 / 1000 份合成目录上的命中率 | 只测目录路线 |

结论：**没有基于向量检索的制度问询评测集。**

### 4.2 设计

**目标**：同一套题比较三种定位（目录路线 / 向量 / 混合）和不同模型，分「定位」和「作答」两层打分。

**语料两套**

- 合成语料（公开，放 brightrule）：在现有种子上扩到 60–100 份制度，覆盖集团 + 2–3 家下属公司、同名不同标准、转发、参照执行、试行、已废止、草稿、限定范围；带单位树、成员关系和每家公司若干员工账号。另加 1,000–2,000 份干扰制度测规模（吸收 #8）。**干扰项要有正文**，至少同名不同单位的那部分要有，否则对向量路线等于没有干扰。
- 真实脱敏语料（不进公开仓库）：从约 1,750 份里挑常用的 50–100 份出题，目录用全量。130 题原题找回后并入。

**题型与配比**（合成约 250 题；真实 130 题起）

| 题型 | 占比 | 测什么 |
|---|---|---|
| 直接事实（数额、天数、审批人） | 22% | 基本准确率 |
| 口语改写 / 同义 | 14% | 向量的主要收益点；问法取自线上真实提问，不对着条文反写（否则词面泄漏） |
| 计算 | 5% | 算式和数字可核 |
| 单位口径（本公司 / 集团 / 平级） | 14% | 提问人身份是否被用对 |
| 职级 / 岗位分档 | 5% | 不知职级时是否全列 |
| 跨条、例外、附则、附件、引用另一份 | 10% | 整份阅读是否漏读 |
| 无依据 | 12%（≥30 题） | 正确拒答、不编造 |
| 权限：问看不到的制度（平级、限定范围、草稿、已废止） | 8%（每个子类 ≥5 题） | 不泄露内容、不作依据 |
| 反问：该问的问一次，不该问的不问 | 5% | 反问精确率和召回率 |
| 指定制度（资料包） | 5% | 回归强项 |
| 跨制度冲突 | 2–4 题，单独报告 | — |

另含少量多轮题：自报单位后沿用、中途换话题。

**每题标注**：问题；提问人 persona（所属单位、职级、账号）；期望制度 id 列表；期望条号；关键数值；答案要点；是否应反问；禁止出现的制度或内容（判泄露）；题型标签；问法来源（线上 / 编写）。

**评分口径**

- 定位层：三条路线统一用「轨迹里实际 `get_record` 读到的制度 id」算制度级 recall@1 / @3 和 MRR（目录路线的定位本身就由模型完成，不可能脱离模型）。向量和混合另报不经模型的纯检索分：条级 recall@5 / @10。
- 作答层：正确 2 / 部分 1 / 错 0（与 130 题口径一致）；出处正确率（制度 + 条号）；引文逐字可核率（脚本）；编造率；无依据正确拒答率；反问精确率 / 召回率；泄露数；时延中位 / p90；输入 token。
- 权限另做不经模型的确定性测试：以各 persona 身份直接读目录和检索，结果里不得出现不可见制度。#3、#5 落地前，权限题测的只是「模型是否听话」，单独标注，不算零容忍门槛。
- 判分：数值、条号、制度 id 用规则判；答案要点用模型盲评。每个配置至少 3 轮，报轮间噪声。
- 门槛（建议，待定）：参照问数的分档，清晰题 ≥95%，无依据 ≥90%，反问 ≥80%，权限隔离落地后泄露 0。

**驱动要求**：要新写一个走 ask 对话路由的驱动，以 persona 账号登录（cloud#5099 的单位块只给登录会话，MCP 和 API key 都看不到）；反问时按 persona 自动回答一轮。现有 `mcp-eval.mjs` 保留，用来测企业版客户自带模型经 MCP 的路径。

**成本**：250 题 × 3 轮 × 3 种定位 ≈ 2,250 次对话。向量路线和资料包题的模型费按问数基线的量级（Haiku 每 280 次约 1.2 美元）可以忽略；目录路线在全量目录上单题可能到数百万 token，真实语料组要先限量试跑。

### 4.3 放 brightrule 还是 cloud 评测台

| | 放 brightrule | 放 cloud 评测台（真实端点驱动） |
|---|---|---|
| 仓库可见性 | **公开**：只能放合成语料和题目；真实题目和答案不能进 | 私有，但客户真实语料同样不宜进产品仓库 |
| 和被测对象的距离 | 技能、资料包、知识源元数据都在这里，改完同仓回归 | 隔着仓库，要钉应用和题集版本 |
| 能否测平台改动 | 需要一个已部署环境 | 能直接起 objectos-ee + 当前平台代码，检索、切段、提问人块等平台改动当场回归 |
| 模型 | `mcp-eval.mjs` 走客户自带模型（DeepSeek 等），贴近企业版客户 | 走网关（Haiku 等），贴近托管 |
| 能否交给客户 | 能：随应用交付，客户用自己的题、自己的模型跑 | 不能 |

**推荐：题集一份，源头放 brightrule。** 合成语料、题目、标注格式和评分器放 brightrule `scripts/eval/`；真实脱敏题集放仓库外（项目文件夹或客户侧），驱动按路径读取；cloud 评测台钉 brightrule 题集版本，当作夹具引用（像 cloud#5031 的 fixtures），做平台回归。
