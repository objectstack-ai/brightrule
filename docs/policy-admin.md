# 制度管理员、上级制度与 AI 建议（#48 设计说明）

> 状态：**待维护者在 PR 上确认。**对应 issue #48（专题 #3）。基于 #45 的扁平结构（制度 + 制度附件）。
> 本卡建字段、对象、权限集、按钮和种子；**诊断逻辑本身不做**（第 5 节）。已发布、多公司隔离等可见性规则仍在 #10，按 [`visibility.md`](visibility.md) 做。

## 1 上级制度 `parent_policy`

制度上的查找字段，指向另一份制度，单选，放在「关联制度」分组，「全部制度」列表里也有一列。用于下属公司转发、参照执行的集团制度，以及层级上的上位制度。被指向的制度在记录页上自动出现「下级制度」相关列表（平台按反向查找生成，标题为「制度 · 上级制度」）。

- **不能指向自己**：钩子 `brightrule_policy_parent`（`src/qa/policy-parent.hook.ts`，插入、更新前）拒绝，返回 400「上级制度不能选本制度自己，请改选另一份制度，或不填。」不改上级制度的保存不检查。
- 更长的环（A → B → A）不检查（第 6 节待确认 1）。
- 导入时自动匹配上级制度另行处理，本卡不做。示例数据里的五份制度都是集团制度，没有自然的上下级，所以种子不填这个字段。

## 2 AI 建议 `brightrule_policy_suggestion`

AI 诊断一份制度时提出的一条建议，主从挂在制度下（`sharingModel: controlled_by_parent`，制度删除时级联删除）。记录名是自动编号「JY-00001」。

| 字段 | 类型 | 说明 |
|---|---|---|
| `suggestion_no` 编号 | 自动编号 `JY-{00000}` | 记录名 |
| `policy` 所属制度 | 主从 → 制度，必填 | |
| `category` 类别 | 选择，必填 | **草案，诊断维度待业务确认**：表述歧义 `ambiguity`、可执行性 `enforceability`、条款缺失 `missing_clause`、内部矛盾 `internal_conflict`、与其他制度冲突 `cross_policy_conflict`、引用已废止制度 `abolished_reference`、合规性 `compliance` |
| `severity` 严重程度 | 选择，必填 | 高 `high` / 中 `medium`（默认）/ 低 `low` |
| `article` 涉及条款 | 文本（200） | 如「第五条」；针对全文的建议为空 |
| `quote` 原文摘录 | 长文本 | 取自脱敏正文 `body_md`，不取原件 |
| `finding` 意见 | 长文本，必填 | |
| `suggestion` 建议改法 | 长文本 | |
| `related_policy` 相关制度 | 查找 → 制度 | 冲突、引用已废止制度时指向对方 |
| `status` 处理状态 | 选择 | 待处理 `open`（默认）/ 讨论中 `discussing` / 已采纳 `accepted` / 不采纳 `rejected` |
| `batch_id` 诊断批次 | 文本（64） | 同一次诊断写入的建议共用 |
| `diagnosed_at` 诊断时间 | 日期时间 | |
| `run_info` 运行记录 | JSON | 模型、token、耗时、诊断维度、正文内容哈希 |

讨论用平台记录自带的评论和 @ 提及（对象的 `enable.feeds`，平台默认开启，对象上显式写明），不另设讨论字段。

视图：「全部建议」和「待处理 / 讨论中」两个列表；制度记录页上有「AI 建议」相关列表。导航：「制度维护」下「全部制度」之后加「AI 建议」。

种子：在《差旅费报销管理办法》上放两条合成建议（一条表述歧义、待处理；一条与《考勤与休假管理制度》口径冲突、讨论中），`run_info` 注明「合成示例，非 AI 生成」。

## 3 权限集与能力

员工原来没有任何权限集，什么都读不了。本卡加两个权限集（`src/security/`）和一个自定义能力。

| 权限集 | 绑定方式 | 授予 |
|---|---|---|
| 问询人 `brightrule_inquirer` | `isDefault: true`：启动时自动绑定到平台内置的 `everyone` 岗位，即所有登录员工 | 读制度、读制度附件、读条款；新建问询、读问询（问询对象私有，只看得到自己的）。**AI 建议无任何权限，不授予任何能力** |
| 制度管理员 `brightrule_policy_admin` | 按人分配：在 `sys_user_permission_set` 里加一行（用户、`permission_set: brightrule_policy_admin`），管理后台或 `POST /api/v1/data/sys_user_permission_set` | 制度、制度附件、条款、问询、AI 建议：增删改查，且看全部、改全部（越过共享）；能力「制度诊断」 |

**能力「制度诊断」 `brightrule.policy_diagnose`**（ADR-0066 三分：能力由包声明、权限集授予、资源要求）：

- 声明：`src/security/capabilities.ts` 用 `defineCapability` 声明（标签「制度诊断」，`scope: 'org'`），由 `objectstack.config.ts` 的 `capabilities` 交给平台，启动时以本包名义登记。命名沿用平台的「包名.能力」写法（如 `setup.access`）。
- 授予：制度管理员权限集的 `systemPermissions`。
- 要求：「AI 诊断」动作的 `requiredPermissions`；「AI 建议」导航项的 `requiredPermissions`。

注意：

1. 平台的开发管理员（`admin@objectos.ai`）也**没有**这个能力，点「AI 诊断」同样 403；要用就给自己分配制度管理员。
2. 导航项按能力而不是按「能否读 AI 建议」隐藏：服务端下发应用导航时只按能力过滤，不会去掉读不了的对象入口。两者现在只由制度管理员同时授予，数据本身仍由对象权限把守。
3. 问询人读得到**全部**制度（含草稿、已废止）。只看已发布、按发文单位隔离是行级规则，在 #10 做；本卡不加行级规则。

## 4 AI 诊断按钮 `brightrule_policy_diagnose`

制度记录页头部（`record_header`）的动作，`type: 'script'`。

- **权限**：`requiredPermissions: ['brightrule.policy_diagnose']`。同一声明两处生效：平台动作入口（`POST /api/v1/actions/brightrule_policy/brightrule_policy_diagnose`、MCP `run_action`）对没有该能力的调用者返回 403；控制台按当前用户的能力隐藏按钮。
- **现在的行为**：沙箱脚本体只返回 `{ ok: true, message: 'AI 诊断功能开发中' }`，界面提示「AI 诊断功能开发中」。脚本体不授予任何 `ctx.api` 能力（`capabilities: []`），写不了任何数据。
- 不对 AI 开放（没有 `ai.exposed`）。

## 5 为什么诊断逻辑另行立卡

诊断要做的是：读制度正文（和附件、相关制度）、调用模型按维度找问题、按批次写入 AI 建议，超长制度还要分段。平台的沙箱脚本（动作体、钩子体）**不能调用 AI**，所以这件事做不成本卡的按钮体。可选的路：

1. 代码插件里的**注册函数**：按钮调用注册函数，函数里调用模型、写建议。只能在**自建企业版**部署里用（云环境不加载应用代码插件）。
2. 等平台的「**问 AI**」动作（`ask_ai`）：在动作里直接把制度交给平台的 AI，按约定的输出写入建议。

选哪条、诊断维度（第 2 节类别）、提示词和超长制度的处理，在新卡里定。按钮、权限和存放建议的子表本卡已就位，接上即可。

## 6 实测（2026-11-26，本地 `pnpm dev`）

两个新建用户：制度管理员（分配了 `brightrule_policy_admin`）、员工（只有默认的问询人）。

| 检查 | 制度管理员 | 员工 |
|---|---|---|
| 制度页「AI 诊断」按钮 | 看得到，点击提示「AI 诊断功能开发中」 | 看不到 |
| 直接调用动作接口 | 200，返回提示 | 403 |
| 「AI 建议」导航、相关列表 | 有 | 没有；直接打开列表页提示对象不存在或无权访问 |
| AI 建议列表、详情、新建、修改（REST） | 都可以 | 全部 403 |
| 读制度、制度附件 | 可以 | 可以 |
| 上级制度选本制度 | 400，中文提示 | — |

自动化测试：`src/qa/__tests__/policy-parent.test.ts`（钩子单测）、`src/security/__tests__/policy-admin.test.ts`（真实引擎上的两个用户，覆盖上表）。
