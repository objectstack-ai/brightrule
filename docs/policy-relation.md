# 制度关系 `brightrule_policy_relation` 设计说明

> 状态：**待维护者在 PR 上确认。**对应 issue #23（专题 #3；详细设计《制度问询与知识检索》2.2「制度关系」、B1.3）。与 #22 的 [`policy-document.md`](policy-document.md) 同一 PR 评审。
> 本卡只建对象、钩子、视图和种子。导入时的自动抽取另立卡；AI 沿关系读相关制度在专题二期；「员工只看已确认的关系」的权限规则在 #10。

## 1 做什么

记录一个**制度版本**与其他制度之间的关系：依据、引用、配套、替代 / 废止。对方可以在库里（`to_policy`），也可以不在库里（如法律法规、尚未导入的制度），这时 `to_policy` 为空，只记名称 `to_title`。

制度很少单独成立（「报销流程按《费用报销管理规定》执行」）。这张表是导入时自动抽取（另卡）和 AI 跨制度找答案（场景 D，二期）的基础。

## 2 字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `from_version` | 主从 → `brightrule_policy_version`，必填 | 关系出自哪个版本；权限跟随父记录（`sharingModel: controlled_by_parent`）；版本删除时级联删除 |
| `from_policy` | 查找 → `brightrule_policy` | 钩子从版本带出；与版本不一致则拒绝。用于按制度查询 |
| `relation_type` | 选择，必填：依据 `basis` / 引用 `cites` / 配套 `supplements` / 替代 / 废止 `supersedes` | 不设「冲突」 |
| `to_policy` | 查找 → `brightrule_policy` | 对方制度；库外制度为空 |
| `to_title` | 文本（200），必填 | 对方名称，如《费用报销管理规定》；nameField，也是唯一参与快速搜索的字段。选了 `to_policy` 而没填名称时由钩子带出 |
| `from_articles` | 文本（200） | 出现在本版本哪几条，如「第三条、第十四条」 |
| `confirmed` | 布尔，默认 false | 已确认；未确认的关系员工看不到，也不作依据（权限规则在 #10） |
| `source` | 选择：导入抽取 `extracted` / 手工 `manual`（默认） | |

视图：「全部关系」（出自版本、关系类型、对方名称、对方制度、出现条款、已确认、来源）；列表视图 `pending`「待确认关系」（`confirmed = false`）。导航：「制度维护」分组，「版本文档」之后依次为「制度关系」「待确认关系」。

## 3 已定事项（维护者 2026-11-25）

- **挂在版本上，不挂在制度上**：主从父记录是版本（`from_version`）。理由：
  - 不同版本引用的制度可能不同（V2.0 引用的规定，V3.0 可能已不再引用）；
  - #10 让员工只见现行版本后，关系的权限随父记录一并继承，不需要另写规则；
  - 版本删除时，它的关系一并删除。

  `from_policy` 保留，由钩子从版本带出，只用于按制度查询。**详细设计 2.2 的示例代码把关系挂在制度上，与 B1.3 矛盾；以本卡为准。**[`design-record-scoped-ai.md`](design-record-scoped-ai.md) 第 6 节的提案（`from_policy` 为主、`from_clause`、`note`、含「冲突」）同样以本说明为准，那个文件本身不改。
- **4 种关系**，不建「冲突」：冲突属于诊断结论，不给员工看。
- **库外制度也记**：`to_policy` 为空，只记 `to_title`。
- **「替代」只记录**：确认后不自动把对方制度改为废止；自动废止另行讨论。
- **员工只看已确认的关系**：写进 #10，本卡不做权限集。

## 4 钩子

`PolicyRelationHook`（`src/qa/policy-relation.hook.ts`，`beforeInsert` / `beforeUpdate`），已登记到 `policyQaHooks`。写法与 #22 的 `PolicyDocumentHook` 相同：处理函数不引用外部名称（辅助函数、拒绝代码都内联），`os build` 把它降为纯元数据的 body（已在构建产物 `dist/objectstack.json` 里确认，与 `PolicyDocumentHook` 形态一致）。

| 规则 | 拒绝代码 | 中文提示 |
|---|---|---|
| 只给版本时带出 `from_policy`；给了不一致的制度则拒绝；换版本时制度随之更换 | `RELATION_POLICY_MISMATCH` | 制度关系的「出自制度」必须是「出自版本」所属的制度。只选版本即可，出自制度会自动带出。 |
| 版本不存在或无权读取 | `RELATION_VERSION_NOT_FOUND` | 找不到所选的制度版本，或你无权读取它。 |
| `to_policy` 等于 `from_policy`（同一制度的新旧版本由版本状态区分，不用「替代」） | `RELATION_SELF_REFERENCE` | 对方制度不能是本制度。同一制度的新旧版本由版本状态区分，不用「替代」关系表达。 |
| 同一版本内，同一关系类型 + 同一对方不能重复 | `RELATION_DUPLICATE` | 本版本已有同一类型、指向同一对方制度的关系，不能重复添加。 |

细则：

- **「同一对方」怎么判断**：填了 `to_policy` 时按制度 id；库外（`to_policy` 为空）时按规范化后的 `to_title`——去掉所有《》书名号，再去掉首尾空白。所以「《费用报销管理规定》」和「 费用报销管理规定 」算同一个。库内关系与同名的库外关系不算重复（判断键不同）。
- **更新时排除自己**：查重时跳过本条记录。
- **只在相关字段变化时才检查**：更新只涉及 `confirmed`、`from_articles`、`source` 时不读库、不检查（确认一条关系不会因为别处数据变化而被拒）。相关字段为 `from_version`、`from_policy`、`to_policy`、`to_title`、`relation_type`；检查时用「本次提交的值，否则原值」。
- **带出对方名称**：填了 `to_policy` 而 `to_title` 为空（或只有空白、书名号）时，读对方制度名称，写成 **《名称》**——与从正文抽取出来的名称写法一致，方便查重和展示。调用方给了名称则不改。
  - 更新时把 `to_policy` 换成另一制度、同时没给新名称，也重新带出，避免名称还停留在原对方（维护者 2026-11-25 确认）。同一次更新给了名称，以给的为准。
- 版本不存在时，REST 写入在钩子之前就被平台的主从权限检查拒绝（「需要对所属制度版本有编辑权限」，英文提示）；钩子的 `RELATION_VERSION_NOT_FOUND` 是在平台放行时的兜底，单测覆盖。

## 5 `from_policy`、`to_title` 不设 `readonly`

与 #22 相同：平台对每一次非系统写入都会剥掉 `readonly` 字段，钩子里的写入不一定是系统写入，设了 `readonly` 钩子就写不进去。谁能改交给权限集（#10）。

## 6 种子

3 条，均为合成制度或虚构名称：

| 出自版本 | 类型 | 对方 | 出现条款 | 已确认 | 来源 |
|---|---|---|---|---|---|
| 差旅费报销管理办法 V3.0 | 引用 | 《费用报销管理规定》（**库外**，`to_policy` 为空） | 第十一条 | 是 | 手工 |
| 差旅费报销管理办法 V3.0 | 引用 | 考勤与休假管理制度（库内） | 第八条 | 是 | 手工 |
| 合同管理办法 V2.0 | 引用 | 反商业贿赂与利益冲突管理规定（库内） | 第十五条 | **否** | 导入抽取 |

种子不填 `from_policy`，由钩子带出。种子的匹配键为 `['from_version', 'relation_type', 'to_title']`（复合键），重放不重复插入。

## 7 实测（2026-11-25，本地 `pnpm dev`，SQLite，全部为合成数据）

| 项目 | 结果 |
|---|---|
| 种子加载 | 32 行全部写入（含 3 条关系）；3 条关系的 `from_policy` 均由钩子带出 |
| 在版本下看关系 | 按 `from_version` 过滤差旅费 V3.0，返回其关系 |
| 「待确认关系」 | `confirmed = false` 只返回 1 条（合同管理办法 V2.0 → 反商业贿赂规定） |
| 指向自己 | 差旅费 V3.0 →「替代」差旅费报销管理办法：拒绝，返回 `RELATION_SELF_REFERENCE` 的中文提示 |
| 重复（库外） | 差旅费 V3.0「引用」「 费用报销管理规定 」（无书名号、带空格）：拒绝，`RELATION_DUPLICATE` |
| 重复（库内） | 差旅费 V3.0「引用」考勤与休假管理制度：拒绝，`RELATION_DUPLICATE`（实测时种子为「配套」，之后改为「引用」，判断逻辑相同） |
| 制度与版本不一致 | 拒绝，`RELATION_POLICY_MISMATCH` 的中文提示 |
| 带出对方名称 | 只给 `to_policy` = 合同管理办法、不给 `to_title`：写入成功，`to_title` 为「《合同管理办法》」。平台的必填检查在钩子之后，不会抢先拒绝 |
| 只改无关字段 | 把上一条确认、改出现条款：成功 |
| 更新时排除自己 | 只改上一条的 `to_title`：成功；改成与已有关系相同的类型和对方：拒绝，`RELATION_DUPLICATE` |
| 版本不存在 | 被平台主从权限检查先拒（英文提示），见第 4 节 |

## 8 待确认

已定（维护者 2026-11-25）：种子里差旅费 V3.0 → 考勤与休假管理制度改为「引用」（「配套」专指实施细则对应主办法）；更新时换了对方制度而没给新名称，重新带出名称。

1. 「库内关系」与「同名库外关系」目前不算重复（例如先手工记了库外《合同管理办法》，后来该制度入库并以 `to_policy` 再记一条）。是否需要在入库时合并，由抽取卡一并考虑。
