# 制度的来源字段：所属单位、印发日期、文件性质、主送、试行（#52 设计说明）

> 状态：**待维护者在 PR 上确认。**对应 issue #52（专题 #3；相关 #48、#10）。基于 #45 的扁平结构（制度 + 制度附件）。
> 本卡建五个字段、试行的派生钩子、视图和种子。导入时自动填写、按所属单位的共享规则（多公司隔离本身）不做（第 6 节）。

## 1 为什么建这五个字段

依据是对约 1,750 份脱敏制度文件（制度信息表、发文通知、目录结构）的统计。真实语料不进本仓库，这里只写统计结论：

- 约 93% 的制度是下属公司发的，制度上却没有「属于哪家单位」，多公司隔离（[`visibility.md`](visibility.md) 维度 2）无从谈起；
- 下属公司大量「转发」「参照执行」集团制度，要和本单位自己印发的区分开，并指向被转发的集团制度（#48 的上级制度）；
- 约 85% 的制度有印发日期、约 18% 的标题带「试行 / 暂行」，原来都没有地方存。

五个字段都能从制度文件本身取得，符合 11-25 会议「源文件里没有的不建」。

## 2 字段

| 字段 | 类型 | 来源 | 分组 | 说明 |
|---|---|---|---|---|
| `owning_unit` 所属单位 | 查找 → 平台业务单元 `sys_business_unit` | 制度文件所在目录（集团机关 / 某下属公司） | 基本信息，「发文单位」之前 | 多公司隔离的基础（第 4 节）。删除仍有制度的业务单元时拒绝（`deleteBehavior: restrict`） |
| `issued_date` 印发日期 | 日期 | 发文通知落款 | 效力，「生效日期」之前 | 与生效日期不同：印发在前，生效可以晚于印发 |
| `issuance_type` 文件性质 | 选择：印发 `issue`（默认）/ 转发 `forward` / 参照执行 `reference` | 标题（「关于转发《……》」）与目录 | 基本信息，「文号」之后 | 转发、参照执行的，「上级制度」`parent_policy` 一般指向被转发的集团制度；不强制，匹配不到时留空由管理员补 |
| `addressees` 主送 | 长文本，原文照录 | 发文通知的主送单位，如「集团机关各部室、各下属企业」 | 基本信息，「决议主体」之后 | 源文件里最接近「适用范围」的原始信息，先存原文，不解析 |
| `is_trial` 试行 | 布尔，默认否 | 标题 | 效力，「状态」之后 | 由钩子根据标题判断（第 3 节），不靠人工勾选 |

原有的「发文单位」`issuing_unit` 保留为文本：它是制度信息表、发文通知上的写法，原文照录；按单位隔离一律看「所属单位」。

视图：「全部制度」列表加所属单位、文件性质（在上级制度之前）、试行、印发日期，去掉发文单位一列（表单里仍有）；「制度库（已发布）」列表加所属单位、试行，去掉发文单位一列。表单按对象上的分组排列，沿用现有分组，不新增分组。

## 3 试行的判断

**规则**：标题含「试行」或「暂行」即为是，如「……管理办法（试行）」「……暂行规定」；否则为否。

钩子 `brightrule_policy_trial`（`src/qa/policy-trial.hook.ts`，插入、更新前）：

- 新建：按标题设置，不管提交的值是什么；
- 改标题：按新标题重新判断，去掉「试行」后变为否，加上「暂行」后变为是；
- 不改标题的保存（标题不在提交内容里，或表单原样提交了同一个标题）：不动试行。管理员手工更正的值保留到下次改标题为止。

钩子是自包含的，`os build` 把它降为纯元数据的脚本体（`dist/objectstack.json` 里 `body.language: js`、`capabilities: []`）。

**为什么不用公式字段或只读字段**：

1. 公式字段（`formula`）在读取时计算、不落库，不能按它筛选、分组和统计，「试行制度有多少」「只看试行」都做不了。
2. 带表达式的存储字段（`expression`）落库，但每次保存都由引擎按表达式重算，提交的值一律不算数，管理员没法更正个别误判（标题里有「试行」二字但并非试行制度，或反过来）。钩子只在新建、改标题时判断，留出了更正的余地。
3. 不设 `readonly`：平台会从非系统写入里去掉只读字段，管理员的更正和钩子的写入都会被去掉。

## 4 所属单位为什么是查找、不是文本

**结论**：查找平台业务单元 `sys_business_unit`。issue 里的退路（「若平台业务单元不能被应用对象引用，退为文本」）不需要。

依据：

1. 业务单元是平台对象（`@objectstack/platform-objects` 的 `SysBusinessUnit`：`isSystem: true`、`managedBy: 'platform'`），接口默认开放读写（不限制 `apiMethods`），自带上下级树 `parent_business_unit_id`。
2. 字段协议只禁止查找指向元数据存储表（`sys_metadata`、`sys_metadata_history`，见 `@objectstack/spec` 的 `field.zod.ts` 关于 `reference` 的说明），其余 `sys_*` 对象可以引用；`pnpm validate` 通过，真实引擎上按名称解析种子、选择业务单元都正常（第 7 节）。
3. 多公司隔离要用的共享规则（接收方「本单位及下级单位」`unit_and_subordinates`）认的是业务单元树。文本对不上树，迟早还要再改一次。

**与平台的 `owning_business_unit_id` 不是一回事**：平台在每个可归属对象上注入了一个同样指向业务单元的系统列 `owning_business_unit_id`（ADR-0117），但它是服务端盖章的归属锚点，只读、隐藏，盖章逻辑尚未上线，现在没有任何东西写它，应用也写不进去。所属单位是制度文件自己的业务属性（文件放在哪家单位的目录里），由导入和管理员填写。多公司隔离那张卡要定：共享规则按 `owning_unit` 写，还是等平台盖章上线后把 `owning_unit` 同步到 `owning_business_unit_id`。

**集团机关发的制度**属于集团这一级的业务单元（种子里是树根「示例集团」），这样按「本单位及下级单位」共享时，集团制度覆盖全集团，下属公司的制度只覆盖本公司及其下级，正对应 [`visibility.md`](visibility.md) 维度 2 的规则。若客户的业务单元树里「集团机关」是与下属公司并列的一个节点，集团制度应挂在它们共同的上级上，由多公司隔离那张卡定。

元数据里不写任何单位名称；单位由客户在平台的业务单元里维护。

**读业务单元的权限**：平台不给普通用户读业务单元的权限，员工和制度管理员读制度时「所属单位」只显示一串编号，制度管理员的选择框也列不出单位（实测 403）。所以两个权限集都加了业务单元的**只读**（`sys_business_unit: { allowRead: true }`）：问询人读得到单位名称，制度管理员能在选择框里选单位。新建、修改业务单元仍只有平台管理员能做。

## 5 种子

全部为合成数据，名称都带「示例」：

- 业务单元三个：示例集团（树根）、示例甲公司、示例乙公司（都在示例集团之下），编码 `DEMO-GROUP` / `DEMO-A` / `DEMO-B`。种子以平台对象的名字和它写入的四个字段声明，不引入平台对象的定义。
- 原有五份集团制度：所属单位示例集团，文件性质印发，主送「集团机关各部室、各下属企业」，补了印发日期（都不晚于生效日期）。
- 新增三份下属公司制度，各带一条条款和一份合成原件占位文件（`fixtures/originals/`）：

| 制度 | 所属单位 | 文件性质 | 上级制度 | 试行 |
|---|---|---|---|---|
| 关于转发《合同管理办法》的通知 | 示例甲公司 | 转发 | 合同管理办法 | 否 |
| 关于参照执行《信息安全管理规定》的通知 | 示例乙公司 | 参照执行 | 信息安全管理规定 | 否 |
| 档案管理办法（试行） | 示例乙公司 | 印发 | — | 是 |

种子直接写明试行的值（与钩子的规则一致），单测核对二者相符。

## 6 不做

- **导入时自动填写这些字段**：导入工具已不在本仓库（#49 删除了 `tools/redact`），由导入工具所在处按本说明的字段配合实现。语料统计里与导入有关的结论，供那边参考：
  - 「类别」「层级」的取值要规范化，原件里写法不一（如「经营类」对应「经营管理类」，「三级级管理制度」应为「三级管理制度」）；
  - 单元格里的「/」按空值处理；
  - 「责任处室 / 科室」映射到「归口部门」；
  - 「关联制度」与「关联制度/文件」两种表头合并为「关联制度 / 文件」；
  - 制度编码有重复，去重不要只用编码（可加上所属单位、标题或原件内容哈希）；
  - 所属单位取自目录，文件性质取自标题（「关于转发《……》」「关于参照执行《……》」）与目录，转发、参照执行的上级制度按书名号里的名称匹配库内集团制度，匹配不到留空。
- **按所属单位的共享规则**（多公司隔离本身）：另行立卡，依赖业务单元树建好、用户归属到单位。
- **「下次复审日」按试行期自动推算**：另议。

## 7 实测（2026-11-26，本地 `pnpm dev`）

种子落库 35 行（业务单元 3、制度 8 及其原件 8、附件 2、条款 12、AI 建议 2）。以平台开发管理员、一个员工（只有问询人）和一个制度管理员分别调用 REST：

| 检查 | 结果 |
|---|---|
| 种子制度的所属单位、文件性质、上级制度、试行 | 与第 5 节一致；两份下属公司制度的上级制度指向对应的集团制度 |
| 制度管理员新建「……（试行）」并选所属单位 | 试行为是，文件性质为「印发」，所属单位为所选单位 |
| 把标题里的「试行」去掉 | 试行变为否 |
| 标题改为「……暂行……」 | 试行变为是 |
| 原样提交标题并手工勾选试行；之后只改摘要 | 手工值保留 |
| 读业务单元（选择框列出的内容） | 员工、制度管理员都能读到种子里的三个单位；加只读权限之前两人都是 403 |
| 管理员通过接口新建一个业务单元，再填到制度的所属单位 | 可以 |

自动化测试：`src/qa/__tests__/policy-trial.test.ts`（钩子单测：试行、暂行、去掉试行、不改标题）、`src/qa/__tests__/policy-source-fields.test.ts`（真实引擎：文件性质默认值、试行派生、种子的所属单位和上级制度）、`src/data/__tests__/seed-documents.test.ts`（种子覆盖面）。
