# BrightRule 明规 — 产品简报

> 状态：**草案，待评审**。本文记录立项时的定位、架构判断和分期设想；领域模型在
> 设计评审（见 [§7 待决事项](#7-待决事项)）通过前不落代码。

## 1. 一句话定位

**条款级、可追溯效力、问完就能办的集团制度平台。**

- 英文：*BrightRule — Policy Management & AI Policy Assistant*
- 中文：*明规 · 集团制度管理与智能问询*
- 命名：「明」= bright；法律英语里 *bright-line rule* 指界限分明、无歧义的规则。

## 2. 要解决的问题

集团型客户的制度普遍存在：

1. **分散** — 散落在 OA、共享盘、红头文件里，员工找不到。
2. **效力难判断** — 找到的条文未必是现行有效版本，也说不清某个历史日期哪一版有效。
3. **适用范围不清** — 集团制度与子公司制度并存，员工不知道哪条适用于自己。
4. **合规举证难** — 无法证明「员工已知悉」某项制度（阅读确认），审计时说不清。

## 3. 核心设计判断

### 3.1 以「条款」而非「文件」为管理与检索单位

制度拆到「条」入库：回答可精确引用「《差旅管理办法》第十二条」，效力、版本、适用范围也能落到条款粒度。

### 3.2 问答走「目录导航 + 全文阅读」，不默认上 RAG 引擎

制度结构清晰、总量有限（集团通常数百份），智能体像人一样查：

1. 读制度目录（名称 / 适用范围 / 摘要 / 关键词）→ 选出 2–5 份相关制度；
2. 通过 ObjectQL 读取这几份制度的现行条款全文；
3. 作答并引用条款号，注意附则、例外条款与「按第 X 条执行」类交叉引用。

收益：**权限天然正确**（直接按提问人的行级权限读记录，无副本、无同步问题）、
不漏例外条款、几乎零新增基础设施。代价：单次 token 较多、响应较慢（目录可走提示缓存）。

语义召回不足时再补**轻量向量层**（`@objectstack/embedder-openai` + pgvector / SQLite 向量适配器）；
只有当语料扩展到大量未结构化材料（扫描件、会议纪要、批复）或规模到上万份时，才引入 RAGFlow。
RAGFlow 的 DeepDoc 更适合作为**存量文件入库阶段的解析工具**（解析 → 人工校对 → 写入条款）。

### 3.3 平台分工

| 层 | 负责 |
|---|---|
| 制度治理（元数据，零代码） | 制度 / 版本 / 条款模型、起草→审批→发布→废止流程、审计留痕 |
| 权限 | `organization_id` 多组织隔离 + 共享规则（集团发文全员可见、子公司发文本公司可见）+ 密级；条款权限继承制度主表 |
| 问答 | ObjectOS `ask` 智能体 + 「制度问询」skill；或开源版经 MCP 接客户自有大模型 |
| 办理 | 「怎么办」类问题直接引导或发起对应业务流程（actions as tools） |

## 4. 领域模型（初稿，待评审）

命名空间 `brightrule`，对象名统一 `brightrule_` 前缀。**不要使用裸 `policy`**——平台中
policy 大量指权限 / 安全策略，会造成 AI 与沟通上的混淆。

| 对象 | 说明 |
|---|---|
| `brightrule_policy` | 制度主表：编号、名称、分类、发文单位、归口部门、适用组织、密级、状态、生效日、废止日、目录摘要、关键词 |
| `brightrule_policy_version` | 制度版本：版本号、修订说明、生效区间；修订产生新版本，旧版本标记为废止，不原地改 |
| `brightrule_clause` | 条款（主从，权限由主表控制）：章 / 条号、条文正文、所属版本 |
| `brightrule_category` | 制度分类体系 |
| `brightrule_policy_relation` | 制度关系：依据 / 替代 / 引用 / 冲突 |
| `brightrule_attestation` | 阅读确认：谁、何时、确认了哪一版 |
| `brightrule_question` | 问询记录：答不上 / 被点踩的问题回流给制度办 |

## 5. 分期

| 期 | 范围 |
|---|---|
| **一期** | 制度 / 版本 / 条款模型 + 审批发布流程；导入一个子公司约 50 份制度；问询 skill 跑通「带引用的问答」；30–50 道真实问题做准确率基线 |
| **二期** | 多组织 + 集团 / 子公司两级权限；版本与废止机制；**阅读确认**；「答不上的问题」闭环 |
| **三期** | 外规库 + 内外规映射（外规变化提示内规修订）；企业微信 / 钉钉入口；新制度发布推送；制度冲突检测 |

每一期都用同一组真实问题回归；管理员测试通过后再全员开放。

## 6. 竞品格局（2026-11 调研，多为厂商自述）

| 类别 | 代表 | 特点 |
|---|---|---|
| 专业制度管理 | NAVEX PolicyTech + Nira、Mitratech PolicyHub、Ideagen Compliance（原 ConvergePoint）、PowerDMS | 生命周期、版本、阅读确认、审计留痕是标配；文档粒度；AI 问答为近一年新增（Nira：仅基于有权访问的已批准制度作答） |
| GRC 平台 | ServiceNow Policy & Compliance、Diligent、IBM OpenPages | 强在外规→内规→内控映射与合规监控；重、贵，员工自助问答不是重点 |
| 国内 OA / 知识管理 | 蓝凌 aiKM、泛微采知连、各类 AI 知识库方案 | 依托 OA 生态，文档级 RAG 为主，缺条款级结构与严格的效力管理 |

差异化：**条款级**粒度、**按日期回溯的效力判断**、**直接按行级权限读取的 AI 问答**、**问答直达业务流程**、**元数据驱动可扩展**。

政策背景：《中央企业合规管理办法》（2022）将制度建设、合规信息化单独成章。

## 7. 待决事项

1. **问答走哪条路** — ObjectOS `ask`（商业版）还是开源版经 MCP 接客户自有大模型；影响交付与报价。
2. **制度样本** — 需拿到客户 3–5 份真实制度校准领域模型，以及 30–50 道真实员工问题作验收集。
3. **平台前置修复** — `service-knowledge` 的记录变更同步不判断知识源 `where` 条件（废止 / 草稿记录会被索引）。
   若走纯「目录导航」路线可绕开，但启用知识检索前须修复。
