> 状态：**待维护者在 PR 上确认。**对应 issue #9 第 2 项「权限可行性」与第 10 项待定事项；实现分别在 #10（权限集）和多公司隔离（待立卡）。
> 本节取代 [`solution.md`](solution.md) 第 99 行「适用范围……决定签收推送和问询可见性」中「决定问询可见性」的说法：可见性与适用范围分开设计（见第 1 节）。那个文件本身不改。

## 1 两个维度：可见性与适用范围

| | 可见性 | 适用范围 |
|---|---|---|
| 回答的问题 | 谁**能看**这份制度 | 这份制度**管**谁 |
| 性质 | 安全要求，由平台强制 | 业务属性，是制度内容的一部分 |
| 由什么决定 | 生效状态、发文单位、可见档位、岗位职责（第 2 节） | 组织、岗位、人员类别 |
| 实现 | 权限集的行级规则 + 共享规则 | 数据：一期为制度上的「适用范围」原文字段（详细设计 B1.2），以后为结构化子表 |
| 谁用 | 每次读取都生效；AI 以提问人身份读，同样受约束 | AI 判断「这份制度管不管你」、制度库「适用于我」筛选、以后的签收推送 |

适用于你的制度你一定能看，但你能看的不一定适用于你（例：只管驾驶员的规定，车队经理也要能看；集团监督岗能看子公司制度，但这些制度不管他本人）。所以**适用范围不用权限实现**。本文只讲可见性。

## 2 目标：四个维度逐层放开

默认看不到（制度对象私有），按下面四个维度放开。员工最终看到的是前三个维度同时满足的部分；第四个维度在此之上给特定岗位额外放开。

| 维度 | 解决的问题 | 规则 |
|---|---|---|
| 1. 生效状态 | 草稿、旧版本不能当成现行规定 | 员工只看已发布制度的**现行版本**。草稿只对起草部门、审核人、制度办可见；**征求意见**阶段对征求意见范围内的单位、部门可见。旧版本、已废止制度按维度 4 开放 |
| 2. 发文单位 | 兄弟公司互不可见，答复不张冠李戴 | 集团发文 → 全集团；公司发文 → 本公司及下级单位；中间层级同理 |
| 3. 可见档位 | 少数敏感制度不能全员可见 | 两档：**全员**（默认）/ **限定范围**（只给授权名单上的单位、岗位或人员）。不做多级密级 |
| 4. 岗位职责 | 管理、监督岗要越过前三条 | 制度办：全部，含草稿、待发布稿和历史版本；责任（归口）部门：全集团本部门归口的制度，含历史版本；合规、审计、法务：全部已发布制度和历史版本，只读 |

### 三项已定的默认值（维护者 2026-11-25）

1. **可见档位只分「全员 / 限定范围」两档**，不做多级密级。真正需要保密的制度是少数，用授权名单覆盖。**涉及国家秘密的制度不进本系统**（非涉密系统不得存放），系统不为它设计权限。
2. **历史版本**：员工只看现行版本；制度办看全部历史；责任部门看本部门归口制度的历史；合规、审计、法务看全部历史，只读。员工需要查当时有效的规定（如报销争议）时，向责任部门询问；以后可为上述岗位做「按日期查当时有效版本」。
3. **外包、实习等非正式人员**：一期只给正式员工开账号，不单独设计权限。以后开账号时，按人员类别限制为只看「全员」档。

这三项做成**可配置的默认值**，换一家客户可以调整。

## 4 原则

1. **默认拒绝，逐项放开。**漏配一条规则的后果是「看不到」，不是「泄露」。
2. **权限挂在制度上。**版本、版本文档、制度关系都跟随制度（主从、跟随父记录），不在下级对象上重复配置。例外只有「现行版本」：用行级规则在版本和文档上表达。
3. **用行级规则限制，不收回对象读权限**（2026-11-25 #9、#10 评论）。二期资料包（#26）按提问人身份读，读不到的行自然不出现；收回对象读权限会让资料包对员工整包拒绝。
4. **AI 和人一致。**不为 AI 单独写可见性规则。唯一例外是原件：人能看、模型不能看，要等平台字段出域（四期）；在那之前靠「员工不开 MCP」，且**不对 `original_file` 加字段级限制**（否则员工也打不开原件）。
5. **可解释、可审计。**管理员能说清某人为什么看不到某份制度是哪个维度挡住的；限定范围制度的访问留日志。

## 5 平台机制对照

| 规则 | 平台机制 | 落在哪 |
|---|---|---|
| 生效状态（已发布、现行版本） | 权限集行级规则：`status == 'published'`、`version_status == 'current'`；文档 `is_current == true`（#22 保留的字段） | #10 |
| 征求意见阶段可见 | 制度状态增加「征求意见」，按征求范围共享 | 待立卡 |
| 发文单位 | 业务单元树 + 共享规则（接收方 `unit_and_subordinates`）；「发文单位」由文本改为指向业务单元 | 多公司隔离，待立卡 |
| 限定范围 | 可见档位字段 + 按记录共享给授权名单（手工共享，或按记录上的授权人员字段共享） | 待立卡 |
| 岗位职责 | 制度管理员权限集（看全部、改全部）；按岗位、按归口部门的共享规则 | #10（管理员）；其余待立卡 |

行级规则写的是 ObjectQL 过滤条件，字段名直接写（`status == 'published'`），不加 `record.` 前缀；写成平台无法转换的形式时**按拒绝处理**（一条都看不到）。

### 要实测的点

1. 权限集的行级规则与共享规则同时存在时如何叠加（预期：共享规则决定能看哪些制度，行级规则在此基础上筛出已发布 / 现行）。
2. 两级主从「制度 → 版本 → 文档」：版本上的行级规则能否让非现行版本的文档对员工隐藏；不能则在文档上直接用 `is_current == true`。
3. 制度关系的「属于现行版本」：关系上没有现行标记，能否继承版本的行级规则；不能则给关系加一个由钩子维护的现行标记。
4. 行级规则能否读到用户的人员类别（外包、实习限制的前提）。
5. 能否按权限集只对员工关闭 MCP；不能则整个部署关闭 MCP（#9 待定事项）。
