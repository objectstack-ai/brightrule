## 1 两个维度：可见性与适用范围

| | 可见性 | 适用范围 |
|---|---|---|
| 回答的问题 | 谁**能看**这份制度 | 这份制度**管**谁 |
| 性质 | 安全要求，由平台强制 | 业务属性，是制度内容的一部分 |
| 由什么决定 | 生效状态、发文单位、可见档位、岗位职责（第 2 节） | 组织、岗位、人员类别 |
| 实现 | 权限集的行级规则 + 共享规则 | 数据：一期为制度上的「适用范围」原文字段（详细设计 B1.2），以后为结构化子表 |
| 谁用 | 每次读取都生效；AI 以提问人身份读，同样受约束 | AI 判断「这份制度管不管你」、制度库「适用于我」筛选、以后的签收推送 |

适用于你的制度你一定能看，但你能看的不一定适用于你（例：只管驾驶员的规定，车队经理也要能看；集团监督岗能看子公司制度，但这些制度不管他本人）。所以**适用范围不用权限实现**。本文只讲可见性。

## 2 目标：四个维度逐层放开

默认看不到（制度对象私有），按下面四个维度放开。员工最终看到的是前三个维度同时满足的部分；第四个维度在此之上给特定岗位额外放开。

| 维度 | 解决的问题 | 规则 |
|---|---|---|
| 1. 生效状态 | 草稿、已废止的制度不能当成现行规定 | 员工只看**已发布制度**。草稿只对起草部门、审核人、制度办可见；**征求意见**阶段对征求意见范围内的单位、部门可见。已废止制度按维度 4 开放 |
| 2. 发文单位 | 兄弟公司互不可见，答复不张冠李戴 | 按制度的「所属单位」`owning_unit`：集团发文 → 全集团；公司发文 → 本公司及下级单位；中间层级同理 |
| 3. 可见档位 | 少数敏感制度不能全员可见 | 两档：**全员**（默认）/ **限定范围**（只给授权名单上的单位、岗位或人员）。不做多级密级 |
| 4. 岗位职责 | 管理、监督岗要越过前三条 | 制度办：全部，含草稿和已废止制度；责任（归口）部门：全集团本部门归口的制度，含已废止制度；合规、审计、法务：全部已发布和已废止制度，只读 |

### 三项已定的默认值（维护者 2026-11-25）

1. **可见档位只分「全员 / 限定范围」两档**，不做多级密级。真正需要保密的制度是少数，用授权名单覆盖。**涉及国家秘密的制度不进本系统**（非涉密系统不得存放），系统不为它设计权限。
2. **已废止制度**：员工只看已发布制度；制度办看全部已废止制度；责任部门看本部门归口的已废止制度；合规、审计、法务看全部已废止制度，只读。修订覆盖正文、系统里不保留旧正文（#45），员工需要查当时有效的规定（如报销争议）时，向责任部门询问，以原件文件为准。
3. **外包、实习等非正式人员**：一期只给正式员工开账号，不单独设计权限。以后开账号时，按人员类别限制为只看「全员」档。

这三项做成**可配置的默认值**，换一家客户可以调整。

## 4 原则

1. **默认拒绝，逐项放开。**漏配一条规则的后果是「看不到」，不是「泄露」。
2. **权限挂在制度上。**制度附件跟随制度（主从、跟随父记录），不在附件上重复配置。制度下面没有别的层级，也没有例外：已发布与否就是制度自己的状态。
3. **用行级规则限制，不收回对象读权限**（2026-11-25 #9、#10 评论）。二期资料包（#26）按提问人身份读，读不到的行自然不出现；收回对象读权限会让资料包对员工整包拒绝。
4. **AI 和人一致。**不为 AI 单独写可见性规则。唯一例外是原件：人能看、模型不能看，要等平台字段出域（四期）；在那之前靠「员工不开 MCP」，且**不对 `original_file` 加字段级限制**（否则员工也打不开原件）。
5. **可解释、可审计。**管理员能说清某人为什么看不到某份制度是哪个维度挡住的；限定范围制度的访问留日志。

| 限定范围 | 可见档位字段 + 按记录共享给授权名单（手工共享，或按记录上的授权人员字段共享） | 待立卡 |
| 岗位职责 | 制度管理员权限集（看全部、改全部）；按岗位、按归口部门的共享规则 | 制度管理员已在 #48 建好（见 [`policy-admin.md`](policy-admin.md)）；其余待立卡 |

#70 实测到的两个叠加结果（同一测试文件）：

- **多个权限集的读规则取并集。**制度管理员同时持有问询人，只加问询人这条规则时，制度管理员也只看得到已发布制度：制度是 `public_read`，在这种对象上「查看全部」（View All）不越过行级规则。所以制度管理员权限集带一条 `using: 'true'` 的规则，与问询人的规则取并集后看全部，按 id 修改草稿、给草稿加附件也都可以。以后给某个岗位放开（维度 4），也是在那个权限集上加规则，与问询人的规则取并集。
- **平台管理员同样受限。**平台的开发管理员（`admin_full_access`，查看全部）也持有问询人，只看得到已发布制度；要看全部就分配制度管理员，与「AI 诊断」按钮的做法一致（[`policy-admin.md`](policy-admin.md) 第 3 节）。

行级规则写的是 ObjectQL 过滤条件，字段名直接写（`status == 'published'`），不加 `record.` 前缀；写成平台无法转换的形式时**按拒绝处理**（一条都看不到）。

### 要实测的点

1. 权限集的行级规则与共享规则同时存在时如何叠加（预期：共享规则决定能看哪些制度，行级规则在此基础上筛出已发布）。还没有共享规则，留到发文单位隔离时测。
2. 制度上的行级规则（`status == 'published'`）能否让未发布制度的附件对员工隐藏（主从、跟随父记录，预期成立）。**成立**（#70，真实引擎测试 `src/security/__tests__/published-only.test.ts`）：附件对象 `controlled_by_parent`，平台只返回读者读得到的制度下的附件，列表和按 id 读都一样，附件上不用另写规则。
3. 行级规则能否读到用户的人员类别（外包、实习限制的前提）。
4. 能否按权限集只对员工关闭 MCP；不能则整个部署关闭 MCP（#9 待定事项）。

## 8 发文单位隔离的实现（#74）

### 8.1 规则

制度对象 `brightrule_policy` 的 `sharingModel` 从 `public_read` 改为 `private`：默认谁都看不到，再由共享规则按「所属单位」`owning_unit` 放开。

| 制度属于 | 谁能看 |
|---|---|
| 集团（单位树根） | 集团全体（根单位及其所有下级单位的成员） |
| 某公司 / 中间层级单位 X | X 及其所有下级单位的成员 |
| 平级或其他分支的单位 | 看不到 |
| （用户没有归属任何单位） | 一份都看不到（拒绝优先） |
| （制度没有所属单位） | 只有制度管理员看得到（没有规则放开它）。os-4 上 1,917 份制度都有所属单位；问询技能目录里的 `owning_unit $null` 分支（#71）对员工因此不会返回任何制度 |

制度管理员（`viewAllRecords`）照旧看全部。与 #70「只看已发布」叠加：共享规则决定看哪些单位的制度，问询人的行级规则再从中筛出已发布的（`published-only.test.ts` 在私有对象和单位规则下通过）。问询人保留对象读权限（`allowRead`），能看哪些行由共享决定（原则 3）。制度附件是「跟随父记录」，跟着制度一起隐藏，不另写规则。

每个拥有制度的单位一条共享规则：

| 项 | 值 |
|---|---|
| 规则名 | `brightrule_policy_unit_` + 单位 id 的小写拼写（`ruleNameFor`：小写字母和数字照写，大写字母写成 `_` + 小写，`_` 写成 `__`，`-` 写成 `_0`；一一对应，id 大小写不同的两个单位不会撞名） |
| 对象 | `brightrule_policy` |
| 条件 | `{ owning_unit: '<单位 id>' }` |
| 共享给 | 「本单位及下级单位」`unit_and_subordinates`，`<单位 id>` |
| 权限 | 只读 |
| 标签 | 制度按单位共享：<单位名称> |

为什么要每单位一条：平台的 `field` 接收方只支持用户类型的字段，不支持「按记录上的业务单元字段展开为该单位及下级」，所以写不成一条静态规则；单位 id 每个环境都不一样，这些规则也不能写死在 `src/` 里。平台支持之后（平台需求另立卡），改成 `src/` 里的一条静态规则，并删除本节的脚本和规则。

### 8.2 对齐脚本（选项 A）

`scripts/sharing/policy-unit-sharing.mjs`：读出所有制度的所属单位，对每个单位建立或更新它的规则，删除本家族（规则名前缀）里单位已不再拥有制度的规则；前缀以外的规则一概不碰。重复运行结果不变（规则已一致时不写，测试核对了规则的 `updated_at` 不变）。通过平台的共享规则接口 `POST/DELETE {basePath}/sharing/rules` 写，平台在每次写入后立即重新物化这条规则的共享。

**为什么选 A（管理员运行的脚本），不选 B（制度保存时由钩子建规则）：**

1. 规则只在「某单位第一次拥有制度」或「某单位不再拥有任何制度」时才需要变。新建制度、改所属单位、用户换单位、单位挪位置，平台都会自己重新物化，不需要运行脚本（第 8.4 节实测）。需要运行的场合很少，且都在导入或调整单位之后，正好是管理员手上的一步操作。
2. 漏运行的后果是「新单位的制度暂时看不到」，不是泄露（原则 1）。钩子方案漏触发（例如导入走种子回放、跳过触发器）的后果相同，却更难发现。
3. 共享规则是安全管理数据，接口要求 `manage_sharing` 能力。制度管理员没有，问询人更没有；钩子要写它就得 `runAs: 'system'` 提权，等于让任何能保存制度的人间接改共享规则。脚本以有权限的管理员身份运行，留有输出，可先 `--dry-run` 看计划。
4. 每写一次共享规则，平台都会重绑全部规则钩子并把这条规则对整张制度表重算一遍。钩子方案在导入 1,917 份制度时会逐条查询、可能逐条写规则；删除过期规则还要在每次改所属单位、删制度时数剩余制度。脚本一次读完、一次对齐。
5. 沙箱钩子能否写 `sys_sharing_rule` 未实测；平台对提权钩子写身份分配对象有拒绝清单，`sys_sharing_rule` 不在其中，B 也许可行，但上面 1–4 条不依赖这一点。

### 8.3 运维步骤

运行者必须同时满足两条：持有 `manage_sharing`（平台管理员；否则接口返回 403，脚本报错退出），并且能看到**全部**制度（平台管理员，或同时是制度管理员）。脚本按运行者看得到的制度算单位，看少了会误删仍需要的规则；一份制度都看不到时脚本拒绝删除。

```bash
# 先看计划，不写
OS_URL=https://<环境> OS_EMAIL=<管理员> OS_PASSWORD=<密码> node scripts/sharing/policy-unit-sharing.mjs --dry-run
# 执行
OS_URL=https://<环境> OS_EMAIL=<管理员> OS_PASSWORD=<密码> node scripts/sharing/policy-unit-sharing.mjs
# 也可以用 OS_TOKEN=<令牌> 代替邮箱和密码
```

输出 `created` / `updated` / `unchanged` / `removed` 四组规则名。什么时候运行：

- 上线本卡时（见第 8.5 节的顺序）；
- 每次导入制度之后；
- 把制度改到一个以前没有制度的单位之后，或删掉 / 改走某单位的全部制度之后。

不需要运行：同一单位新增制度、在已有规则的单位之间改所属单位、用户换单位或加入单位、单位在树上挪位置、单位改名（改名只影响规则标签，下次运行时更新）。

规则由脚本维护，**不要在设置里手工改**：手工改过的本家族规则，下次运行会被改回（测试覆盖）。

### 8.4 实测（2026-11-28，本地真实引擎，`src/security/__tests__/policy-unit-visibility.test.ts`）

单位树：集团 → 甲公司（→ 甲一分公司）、乙公司；每个单位一名员工、一份制度、一个附件；另有一名未归属单位的员工、一名制度管理员。列表（`find`）和按 id 读（`findOne`，REST `GET /data/brightrule_policy/<id>`）逐条核对一致。

| 用户 \ 制度 | 集团 | 甲 | 甲一 | 乙 |
|---|---|---|---|---|
| 集团本部员工 | ✓ | ✗ | ✗ | ✗ |
| 甲公司员工 | ✓ | ✓ | ✗ | ✗ |
| 甲一分公司员工 | ✓ | ✓ | ✓ | ✗ |
| 乙公司员工 | ✓ | ✗ | ✗ | ✓ |
| 未归属单位的员工 | ✗ | ✗ | ✗ | ✗ |
| 制度管理员 | ✓ | ✓ | ✓ | ✓ |

制度附件的结果与上表完全相同。其余各点：

| 要测的点 | 结果 |
|---|---|
| 规则建好之前 | 员工一份都看不到，制度管理员看全部 |
| 没有 `manage_sharing` 的人运行脚本（制度管理员） | 403，脚本报错，一条规则都没写 |
| 运行两次 | 第二次全部 `unchanged`，规则的 id 和 `updated_at` 不变 |
| 某单位不再拥有制度 | 下次运行删除它的规则；本家族以外的规则不动；单位重新拥有制度后，下次运行重建 |
| 新建制度（单位已有规则） | 立即按规则共享，不用运行脚本 |
| 改制度的所属单位（新单位已有规则） | 立即重新共享：原单位的人看不到了，新单位及下级看得到 |
| 用户换单位、退出单位 | 立即跟着变；退出全部单位后一份都看不到 |
| 单位在树上挪位置（甲一挪到乙下） | 立即跟着变：甲一员工改看乙的制度、不再看甲的；挪回后恢复 |
| 手工改过的本家族规则 | 下次运行改回 |
| 制度阅读页（`POST /data/brightrule_policy/<id>/page`） | 看不到的制度答 404 `RECORD_NOT_FOUND`，与「不存在」相同 |
| MCP `get_record` | 看不到的制度答 `RECORD_NOT_FOUND` |
| MCP `query_records` | 只返回看得到的单位的制度 |

### 8.5 os-4 上线前要补的

1. **员工归属到业务单元。**员工必须在 `sys_business_unit_member` 里有一行（用户、单位），且单位是黑猫导入工具建的那棵树上的节点。没有归属的员工上线后一份制度都看不到。本卡**没有**核对 os-4（MCP 不开放系统对象，本卡也不在 os-4 上读写）；上线前请管理员在后台或用 `GET /api/v1/data/sys_business_unit_member` 核对：每个要用制度问询的员工都有归属，归属的是自己所在公司（或其下级）那个节点，而不是同名的另一个节点。
2. **集团机关发的制度挂在树根。**os-4 的 20 个所属单位里，集团机关的制度若挂在一个与下属公司并列的「集团机关」节点上，按本节规则它们只对集团机关的人可见，下属公司看不到集团制度。要么把这些制度的所属单位改为树根，要么把下属公司挂到「集团机关」节点下（[`policy-source-fields.md`](policy-source-fields.md) 第 4 节的待确认项）。
3. **顺序**：先在 os-4 上运行一次脚本（制度还是 `public_read` 时就能建规则），再发布本卡，发布后再运行一次，应全部 `unchanged`，并用两名不同公司的员工各抽查一份对方公司的制度看不到。先建规则再发布，可避免发布与运行之间的「谁都看不到」空档；即使空档出现，后果也只是暂时看不到，不是泄露。
